화성 맵(`Hwaseong Place`, MeshPart 189 + 충돌 Part 992)을 오버데어에 넣었는데
건물이 전부 폐가처럼 부서져 보인다. 장안문·성벽도 마찬가지다.
**배치를 고치려 하지 마라. 배치는 이미 검증했고 정상이다.** 아래를 읽고 조언을 달라.

## 1. 이미 검증한 것 — 다시 재지 마라

측정 경로를 명시한다. "값을 다시 읽어 대조"한 게 아니라 독립 경로로 쟀다.

| 구간 | 검사 | 결과 |
|---|---|---|
| 배치 | MeshPart 189/189 존재 | 정상 |
| 배치 | `CFrame.Orientation` 전부 (0,0,0) | 정상 |
| 배치 | `Size / (2 × UnitExtent)` = **1.000** (189개 전부) | 정상 |
| 배치 | `MeshId` / `TextureId` 빈 것 0개 | 정상 |
| 배치 | 점유 X 42,800~80,000 / Z ±19,200 — 매니페스트 + 델타와 일치 | 정상 |
| 익스포터 | FBX 를 블렌더로 되열어 대조: 삼각형 수 일치, **bbox 오차 0.000 m** | 정상 |
| 익스포터 | 임베디드 텍스처 150/150 파일, 2048px 초과 0 | 정상 |

`UnitExtent.Z` 가 음수라 Z 비율이 −1.000 으로 나오는데 **이건 부호 규약이고 정상**이다.

## 2. 실제 원인 — 원본 메시의 위상이 갈려 있다

연결 껍질(connected shell) 수를 셌다. **면/껍질 비가 2 라는 건 면 2개마다 따로 노는
조각이라는 뜻**이다. 정상적인 용접된 메시는 수백~수천이 나온다.

FBX 실측:

| 파일 | 면 | 껍질 | 면/껍질 | 최악 메시 |
|---|---|---|---|---|
| JAM_01 | 25,614 | 5,157 | **5.0** | `Ceiling_01` **2.0** |
| JAM_05 | 28,563 | 4,793 | **6.0** | `Floor_01` **1.9** |
| JAM_12 | 18,003 | 5,963 | **3.0** | `Roof_04` **3.0** |
| SBK_08 | 12,998 | 3,109 | **4.2** | `G_Stair_001_01` **1.8** |
| HPR_01 | 28,766 | 2,997 | 9.6 | `Cannon_001_01` 3.8 |
| VEG_03 | 23,136 | 11,970 | **1.9** | `OBJ_b5cea4_p00` **1.9** |
| SBK_01 | 20,246 | 536 | 37.8 | (정상) |
| CTB_01 / 40 / 90 | | | 27.8 / 17.5 / 34.3 | (공간 분할이라 껍질 다수는 정상) |

블렌더 원본(`palaces.blend`)에서 같은 값이 나온다 — **익스포터가 만든 문제가 아니라
원본이 이미 갈려 있다.**

```
장안문_Ceiling_01          면 1,356  껍질 678   면/껍질  2.0   ← FBX 와 동일
장안문_G_Stair_001_01      면 7,108  껍질 3,698 면/껍질  1.9
장안문_Floor_01            면 3,902  껍질 1,687 면/껍질  2.3

장안문_B_RoofBoard_001_01  면 2,562  껍질  62   면/껍질 41.3   ← 멀쩡
```

같은 장안문 안에서도 `B_` 접두 메시는 멀쩡하고 나머지가 갈렸다.

느슨한 면들이 좌표상 딱 붙어 있어서 **블렌더 뷰포트에서는 완벽하게 보인다.**
엔진이 LOD 생성이나 메시 최적화를 돌리는 순간 흩어진다 — 그게 폐가처럼 보이는 정체다.

원인 계보: KCISA 스캔을 정규화할 때 `heritage.py` 의 decimate 를 **용접 없이** 돌렸다.
같은 문제를 한옥 3채에서 겪고 `hwaseong/rebake_hanok.py` 로 고친 적이 있다
(용접 `WELD_M 0.008` → 데시메이트 `MIN_RATIO 0.45`. **ratio 가 최종 면 수보다 중요하다 —
0.45 는 멀쩡하고 0.30 은 갈린다**). 그 수정이 JAM·SBK·HPR·VEG 에는 적용되지 않았다.

## 3. 묻고 싶은 것

1. **오버데어가 임포트한 메시에 LOD/최적화를 돌리는 게 맞나?** 느슨한 면을 흩뜨리는
   단계가 어디인지 아는가. 끌 수 있는 속성이 있나
   (`EnableMeshShadowDetails` / `MeshShadowDetailLevel` 말고).
2. 만약 끌 수 없다면 **재발행이 유일한 답인가?** 발행은 되돌릴 수 없어서
   JAM 19 + SBK 8 + HPR 2 + VEG 6 = 35개 파일을 다시 올려야 한다.
   같은 이름으로 다시 올렸을 때 기존 것과 어떻게 구분하는 게 안전한가
   (`createdTime` 최신 선택 말고 더 나은 방법이 있나).
3. **어느 정도 면/껍질 비면 안전한가?** 우리 기준으로 20 이상이면 되나,
   아니면 완전히 하나로 붙어야 하나.
4. 재발행 전에 **레벨에서 한 개만 갈아끼워 검증**할 방법이 있나.
5. 다른 원인 가능성이 보이면 말해 달라. 위 측정에서 놓친 게 있을 수 있다.

## 4. 좌표 규약 — 이 맵은 산곡(JSN_Sangok)과 다르다

산곡 명세서를 그대로 적용하면 안 된다. **네 가지가 다르다.**

| | JSN_Sangok | 화성 |
|---|---|---|
| Y 축 | `Y = bz * 100` | **`Y = bz * 100 + 5000`** (FLOOR_Y) |
| 회전 | `R_e = M·R_b·Mᵀ` → `to_euler('ZXY')` + 월드 Y 180° 보정 | **`Orientation = (0,0,0)` 예외 없음** |
| 피벗 | 마스터는 바닥 중앙이라 로컬 up 으로 h/2 올림 | 월드 좌표가 메시에 구워져 있어 **각자의 bbox 중심 그대로** |
| 원점 델타 | `OFFSET = -60000` (X 만) | **ΔX −58000 / ΔY −5000 / ΔZ 0** |

화성 익스포터는 오브젝트마다 `matrix_world` 를 메시 정점에 구워서 내보낸다.
그래서 **ZXY 분해도 Y180 보정도 쓰면 안 된다** — 넣으면 각 조각이 자기 bbox 중심을
축으로 제자리 회전해서 조립이 통째로 터진다.

같은 이유로 **부재 하나가 틀어져 보인다고 그것만 돌려서 맞추지 마라.**
좌표계 오류를 가려서 다음 그룹에서 같은 문제가 다시 난다.

ΔX 가 −58000 인 이유: 레벨의 `PLACE NEW MAP CENTER HERE` 표지판(X 50000)을 따라
−70000 을 쓰면 맵 서쪽 끝이 X 30,800 까지 내려와 **창덕궁(27,000~33,000)과 22 m 겹친다.**
−58000 이면 X 42,800~80,000 이 되어 창덕궁과 98 m, 나머지와 400 m 이상 여유가 생긴다.

## 6. 안전 규칙 (지켜 달라)

- **발행된 에셋을 다시 올리지 마라.** 중복 발행이고 되돌릴 수 없다.
  재발행이 답이라는 결론이 나면 **먼저 말하고, 어느 파일인지 목록을 확정한 뒤** 진행한다.
- **`level.publish` 를 부르지 마라.**
- **플레이 중에 편집하지 마라** — `game.stop` 먼저.
- **작업 대상 밖을 건드리지 마라** — `JSN_Sangok`(3,396) / `Lobby` / `Changdeokgung Place`
  / `Wakizashi_*` / `GND_Base` / `WarCitySpawn`.
- 매 단계 전에 `%USERPROFILE%\Desktop\ovdr_backup\` 에 백업.
- 배치는 되돌릴 수 있고 **발행만 되돌릴 수 없다.**
